# HSLog Data Source

## 1. Overview

HSLog는 하스스톤 카드 데이터를 직접 수집하거나 임의로 관리하지 않고, HearthSim에서 제공하는 `hsdata`를 주요 원본 데이터 소스로 사용한다.

HSLog는 `hsdata`의 원본 데이터를 기반으로 게임에 필요한 데이터를 생성하며, 출시일과 게임 대상 카드 여부 등 HSLog에서 별도로 판단해야 하는 정보는 데이터 처리 과정에서 관리한다.

전체적인 데이터 흐름은 다음과 같다.

hsdata → Data Processing → HSLog Dataset → Game

## 2. Source

### 2.1 HearthSim hsdata

HSLog의 하스스톤 카드 데이터는 HearthSim의 `hsdata`를 주요 원본으로 사용한다.

`hsdata`에서 제공하는 카드 데이터에는 다음과 같은 정보가 포함될 수 있다.

- 카드 ID
- DBF ID
- 카드 이름
- 카드 텍스트
- 카드 이미지 관련 정보
- 공격력
- 생명력
- 비용
- 직업
- 희귀도
- 카드 타입
- 세트
- 메커니즘
- 수집 가능 여부
- 기타 하스스톤 카드 메타데이터

HSLog는 원본 데이터의 필드를 현재 게임에서 사용하지 않는다는 이유만으로 임의로 제거하지 않는다.

향후 카드 정보 표시, 통계, 게임 모드 확장 등에 활용할 가능성을 고려하여 원본 데이터는 가능한 한 그대로 보존한다.

## 3. Source Data Policy

HSLog의 데이터 처리 원칙은 다음과 같다.

1. `hsdata`를 원본 데이터로 취급한다.
2. 원본 데이터는 가능한 한 변경하지 않는다.
3. HSLog에서 필요한 데이터는 별도의 데이터 처리 과정을 통해 생성한다.
4. 원본 데이터와 HSLog가 추가로 관리하는 메타데이터를 분리한다.
5. 데이터의 예외 사항은 자동 처리보다 명시적인 수동 보정을 우선한다.
6. 게임 실행 시 외부 원본 데이터를 직접 조회하지 않는다.

## 4. Card Data

HSLog는 `hsdata`에서 제공하는 카드 데이터를 기본적으로 그대로 보존한다.

현재 특정 필드만 사용하는 것을 전제로 데이터 구조를 축소하지 않는다.

예를 들어 다음과 같은 필드는 원본 데이터에 존재하는 경우 그대로 유지한다.

- `id`
- `dbfId`
- `name`
- `text`
- `flavor`
- `artist`
- `attack`
- `cardClass`
- `collectible`
- `cost`
- `elite`
- `faction`
- `health`
- `mechanics`
- `rarity`
- `set`
- `type`

실제 게임 로직에서는 이 중 필요한 필드만 사용한다.

이를 통해 향후 카드 정보 UI나 새로운 게임 모드를 추가할 때 원본 데이터를 다시 수집해야 하는 상황을 최소화한다.

## 5. Game Card Eligibility

HSLog의 기본 게임 대상 카드는 `collectible === true`인 카드로 제한한다.

### 5.1 Card Type

카드의 `type`은 기본적인 제외 기준으로 사용하지 않는다.

따라서 다음과 같은 카드 타입은 `collectible === true`인 경우 기본적으로 게임 대상에 포함할 수 있다.

- MINION
- SPELL
- WEAPON
- HERO
- LOCATION
- 기타 실제 플레이 가능한 카드 타입

즉, `HERO`라는 이유만으로 카드를 제외하지 않는다.

예를 들어 Dr. Boom과 같은 영웅 카드는 일반 카드와 동일하게 게임의 비교 대상이 될 수 있다.

### 5.2 Excluded Cards

다음과 같은 데이터는 게임 대상에서 별도로 제외할 수 있다.

- 테스트용 카드
- 내부용 카드
- 실제 플레이어가 사용할 수 없는 카드
- 데이터 오류가 확인된 카드
- 게임 목적에 부적절한 카드
- 기타 명확한 제외 사유가 존재하는 카드

이러한 제외 목록은 데이터 처리 과정에서 명시적으로 관리한다.

## 6. Set Data

HSLog는 카드의 `set` 필드를 카드 출시 시점을 결정하는 핵심 데이터로 사용한다.

카드의 출시일은 개별 카드에 직접 기록하지 않고 `set`을 통해 결정한다.

데이터 관계는 다음과 같다.

Card → set → Set Metadata → releasedAt

예를 들어 특정 카드의 `set`이 `EXPERT1`이라면 `EXPERT1`의 `releasedAt`을 해당 카드의 최초 출시일로 사용한다.

## 7. Set Release Date

### 7.1 Principle

HSLog에서 카드의 최초 출시일은 해당 카드가 속한 `set`의 출시일을 기준으로 결정한다.

동일한 `set`에 속한 카드들은 기본적으로 동일한 최초 출시일을 가진다.

### 7.2 Set Metadata

세트 출시일은 카드 원본 데이터와 별도의 metadata로 관리한다.

예를 들어 `sets.json`은 다음과 같은 구조를 가진다.

- `set`
- `releasedAt`

카드 데이터 자체에는 출시일을 추가하지 않는다.

이를 통해 동일한 출시일을 여러 카드에 중복 저장하지 않는다.

## 8. Set Discovery

HSLog는 `hsdata`에 존재하는 `set` 값을 기반으로 세트 목록을 구성한다.

데이터 업데이트 과정에서 다음 작업을 수행한다.

1. `hsdata`에서 카드 데이터를 가져온다.
2. 카드 데이터에 존재하는 `set` 값을 추출한다.
3. 중복을 제거하여 전체 set 목록을 생성한다.
4. 기존 HSLog의 set metadata와 비교한다.
5. 새롭게 발견된 set이 있는지 확인한다.
6. 새로운 set의 출시일을 확인한다.
7. 필요한 경우 `sets.json`을 수동으로 보정한다.

이를 통해 새로운 확장팩이나 새로운 세트가 추가되었을 때 HSLog 데이터에 반영할 수 있다.

## 9. Release Date Verification

모든 `set`의 출시일을 완전히 자동으로 결정하는 것을 목표로 하지 않는다.

특히 역사적인 세트나 특수 세트는 이름만으로 실제 출시일을 정확하게 판단하기 어려울 수 있다.

따라서 출시일 데이터는 다음 원칙을 따른다.

자동화 가능한 데이터는 자동으로 생성한다.

자동으로 판단하기 어렵거나 예외가 존재하는 데이터는 수동으로 검증하고 보정한다.

최종적으로 HSLog에서 사용하는 출시일 데이터는 검증된 `sets.json`을 기준으로 한다.

## 10. Special Sets

일반적인 확장팩과 다른 방식으로 관리되는 세트가 존재할 수 있다.

예:

- Basic
- Classic
- Core
- Hall of Fame
- Adventure
- Mini-Set
- 기타 특수 세트

이러한 세트는 일반적인 확장팩과 동일한 방식으로 자동 처리되지 않을 수 있다.

특수 세트의 출시일은 실제 최초 플레이 가능 시점을 기준으로 별도로 검증한다.

특히 Core Set과 같이 기존 카드가 다시 포함되는 경우에는 Core Set 편입일이 아닌 카드의 최초 출시 시점을 기준으로 판단하는 것을 원칙으로 한다.

## 11. First Release Date

HSLog에서 사용하는 카드 출시일은 카드의 **최초 출시일(First Release Date)**이다.

카드가 이후 다른 세트에 다시 포함되더라도 최초 출시일은 변경하지 않는다.

예를 들어 특정 카드가 다음과 같은 이력을 가지고 있다고 가정한다.

Original Set → 2015년 최초 출시

Core Set → 2024년 재편입

이 경우 HSLog에서 해당 카드의 출시일은 2015년으로 유지한다.

따라서 단순히 현재 카드 데이터의 `set`만 확인하는 것으로 충분하지 않은 경우에는 데이터 처리 과정에서 최초 출시 세트를 별도로 확인하고 보정할 수 있다.

## 12. Data Processing

HSLog는 원본 `hsdata`를 그대로 런타임에서 사용하는 대신 데이터 업데이트 과정을 통해 서비스용 데이터를 생성한다.

전체 과정은 다음과 같다.

hsdata

↓

Card Data Extraction

↓

Set Discovery

↓

Set Release Date Mapping

↓

Card Filtering

↓

Data Validation

↓

HSLog Dataset

## 13. Data Update

HSLog의 카드 데이터는 사용자가 사이트에 접속할 때마다 외부에서 가져오지 않는다.

대신 별도의 데이터 업데이트 스크립트를 통해 정기적으로 갱신한다.

예상되는 업데이트 과정은 다음과 같다.

1. 최신 `hsdata`를 가져온다.
2. 카드 데이터를 갱신한다.
3. 새로운 `set`이 존재하는지 확인한다.
4. 새로운 `set`의 출시일을 확인한다.
5. 출시일 metadata를 추가하거나 수정한다.
6. 게임 대상 카드 필터를 적용한다.
7. 데이터 유효성을 검사한다.
8. HSLog Dataset을 생성한다.
9. 변경 사항을 Git에 커밋한다.
10. 변경된 데이터를 포함하여 서비스를 배포한다.

## 14. Data Update Script

데이터 업데이트는 별도의 스크립트를 통해 실행할 수 있도록 구성한다.

예:

`npm run update:data`

해당 스크립트는 다음 작업을 수행하는 것을 목표로 한다.

- 최신 원본 데이터 가져오기
- 카드 데이터 생성
- set 목록 추출
- 새로운 set 탐지
- 카드 필터링
- 데이터 검증
- HSLog Dataset 생성

출시일처럼 자동으로 결정하기 어려운 값은 스크립트가 임의로 확정하지 않고 수동 검증이 필요한 상태로 표시할 수 있다.

## 15. Generated Dataset

HSLog는 원본 데이터와 서비스에서 사용하는 데이터를 구분한다.

권장 구조는 다음과 같다.

data/

- cards.json
- sets.json

### cards.json

`hsdata`에서 가져온 카드 데이터를 기반으로 생성한다.

원본 카드 정보는 가능한 한 그대로 유지한다.

### sets.json

HSLog가 별도로 관리하는 세트 metadata이다.

각 set의 최초 출시일을 관리한다.

이를 통해 카드 데이터와 출시일 데이터를 분리한다.

## 16. Version Control

HSLog에서 생성된 Dataset은 Git으로 관리한다.

데이터 업데이트 후 변경된 `cards.json`과 `sets.json`을 저장소에 커밋한다.

이를 통해 다음 사항을 추적할 수 있다.

- 어떤 카드 데이터 버전을 사용했는가
- 언제 새로운 카드가 추가되었는가
- 어떤 set의 출시일이 변경되었는가
- 수동 보정이 언제 이루어졌는가
- 특정 시점의 게임 데이터가 무엇이었는가

따라서 외부 데이터 소스의 변경으로 인해 서비스 데이터가 예기치 않게 변경되는 상황을 방지할 수 있다.

## 17. Runtime Data Dependency

게임 실행 시 HSLog는 외부 `hsdata`에 의존하지 않는다.

사용자는 HSLog에 접속했을 때 이미 검증되고 저장된 HSLog Dataset을 사용한다.

즉, 게임 실행 구조는 다음과 같다.

HSLog Dataset → Game

외부 원본 데이터 업데이트는 게임 실행과 분리한다.

이를 통해 다음과 같은 문제를 방지한다.

- 외부 데이터 소스 장애
- 네트워크 오류
- 원본 데이터의 갑작스러운 변경
- 게임 실행 시 데이터 처리 비용 발생

## 18. Data Integrity

게임에 사용되는 모든 카드는 유효한 출시일을 가져야 한다.

카드의 `set`이 존재하지만 해당 `set`의 출시일을 확인할 수 없는 경우 해당 카드는 게임 데이터에 포함하지 않는다.

또한 다음과 같은 데이터 오류를 검증한다.

- 존재하지 않는 set
- 유효하지 않은 카드 ID
- 중복 카드 ID
- 출시일이 없는 set
- 잘못된 출시일 형식
- 잘못된 카드 데이터
- 게임 대상에서 제외되어야 하는 카드

데이터 검증을 통과하지 못한 데이터는 서비스에 배포하지 않는다.

## 19. Data Source Principles

HSLog의 데이터 관리는 다음 원칙을 따른다.

### Source of Truth

카드 원본 데이터의 주요 출처는 HearthSim `hsdata`이다.

### Preserve

원본 데이터는 가능한 한 그대로 보존한다.

### Separate

원본 카드 데이터와 HSLog가 추가로 관리하는 metadata를 분리한다.

### Verify

자동으로 판단하기 어려운 정보는 수동으로 검증한다.

### Version

서비스에서 사용하는 Dataset은 Git으로 버전 관리한다.

### Reproducible

동일한 Dataset을 사용하면 동일한 게임 데이터를 재현할 수 있어야 한다.
